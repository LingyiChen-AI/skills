# 写作风格

从 36 篇已发布文章里统计出来的，不是拍脑袋定的。照着写。

## 人设

一个自己动手的 AI 博主。装过、跑过、踩过坑，然后把能用的东西讲给同行听。
**不是**科技媒体通稿，**不是**官网文案翻译，**不是**泛泛而谈的行业观察。

说人话。「我实测」「我踩了个坑」「这个值得装」比「业界普遍认为」有用得多。

## 篇幅与结构

| 指标 | 实际值 |
| --- | --- |
| 中文字数 | 1300–1500（中位 1372），不要写成万字长文除非真有那么多料 |
| `##` 小节 | 8–10 个，小节要短，一屏能读完一节 |
| 表格 | 七成文章有，用来做对比、列参数、摆版本差异 |
| 代码块 | 教程类必有；资讯类放配置片段或命令 |
| 加粗 | 平均每篇 31 处，用来标关键结论，不是随便加 |
| 列表 | 平均每篇 24 条 |
| emoji | 平均 3 个，只在引流贴的「获取方式」这类地方用，正文别撒 |

## 开头的四种写法

照抄这几种，不要写「随着人工智能的飞速发展」这类套话：

1. **时间+事件直给** —— 「2025 年 8 月 1 日，国内最知名的 Kubernetes 管理平台 KubeSphere 突然宣布闭源。」
2. **戳痛点，用第二人称** —— 「在 Coze、Dify、ComfyUI 这些低代码平台上搭建复杂工作流，你是不是也经历过：」
3. **先给落差** —— 「Seedance 2.0 发布后，不少人第一时间去火山引擎申请 API 权限，结果发现——个人开发者根本申请不到。」
4. **一句话说清是什么**（介绍类用）—— 「HyperFrames 是 HeyGen 刚刚开源的视频渲染框架，核心理念极其简洁：用 HTML 写视频。」

自己的项目用「大家好，分享一个我开源的项目 —— X」。

## 结尾

给行动指引或留一个判断，不要用「让我们拭目以待」收尾。

- 工具类：「Docker 一键部署，AI 能力配上自己的 Key 就能用。」
- 对比类：「如果你问『哪个更好』，这就像问『iPhone 和 Arduino 哪个更好』——取决于你要做什么。」
- 教程类：把成本和收益摆出来，「配置成本就是今晚 30 分钟，回报是免费跑」
- 资讯类：留一个往前看的判断，「对整个行业来说，真正的故事才刚刚开始。」

常用收尾小节名：`写在最后`、`总结`、`一句话总结`、`适用场景`、`配套资源（全部一手源）`。

## 按类型的骨架

**资讯/爆料** — 事件全景 → 硬数据（benchmark/参数表）→ 为什么重要 → 怎么跟进
**工具评测** — 痛点 → 这是什么 → 核心功能（配图逐个讲）→ 快速上手 → 适用场景
**教程** — 背景（为什么需要这篇）→ 这次到底得到了什么 → 分步操作（每步给命令和预期输出）→ 验证 → 踩坑
**自有项目** — 先看效果 → 解决什么问题 → 核心功能 → 快速部署 → 下一步计划

## 硬性要求

- **数据必须有出处**。参数、跑分、价格、时间线，没核实过就不写。宁可说「官方未公布」。
- **链接贴纯文本 URL**，不要 markdown 链接语法，公众号渲染不了。
- 正文**从 `# 标题` 开始**，不要 frontmatter。
- 小标题用「一、二、三」或直接短语，不要「第一部分」这种公文腔。
- 别写「众所周知」「不言而喻」「赋能」「闭环」「抓手」。
